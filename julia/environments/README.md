# Julia environments

`joint` resolves the engine, its PythonCall bridge and all three device packages
together. `cpu`, `cuda`, `rocm` and `metal` are dependency-closed subsets of that
manifest, generated by `scripts/resolve.jl`. Each shared package has the same UUID,
version, source tree, dependencies and extension declarations. Julia may serialize
weak dependencies differently when their targets are absent from a subset.

The CPU environment directly depends on PythonCall. The engine has only a weak
PythonCall dependency, so its standalone tests do not initialize Python. Device
packages are also weak dependencies, activated by their package extensions.

At runtime, stack the installed environments in this order: `cpu`, `cuda`, `rocm`,
`metal`, followed by `@stdlib`. Omit devices that are not installed. The stack
contains no user or global Julia environment. All application environments refer
to the engine with the relative path `../..`; relocate the copied engine and its
environments together. Setup validates the source and preference identity before
the Python adapter initializes Julia.

`versions.toml` records the qualified Julia and PythonCall pair and exact quality
tool versions. Application manifests are generated on that exact Julia release;
the installer admits the same minor series, with other patch releases reported by
the Python adapter as untested. Changing the Julia minor series requires
requalification of the installer APIs, bridge and device package graph.

Regenerate the manifests from the repository root, using a private depot:

```sh
JULIA_LOAD_PATH=@:@stdlib julia --startup-file=no julia/scripts/resolve.jl
```

Do not edit manifests directly. To update application dependencies deliberately,
update the joint environment with Pkg and then run the generator. A selector
package update also requires reviewing its artifact-selection code and updating
`scripts/artifact_selectors.toml`; unknown or changed selectors refuse setup.

`quality` and `formatter` have separate pinned manifests and are never installed by
normal CPU or GPU setup. Run the development checks from the repository root:

```sh
GROUP=Core JULIA_LOAD_PATH=@:@stdlib julia --startup-file=no --check-bounds=yes \
  --project=julia/environments/cpu \
  -e 'using Pkg; Pkg.test("SolpropJulia"; allow_reresolve=false)'
GROUP=Quality JULIA_LOAD_PATH=@:@stdlib julia --startup-file=no --check-bounds=yes \
  --project=julia/environments/quality julia/test/runtests.jl
JULIA_LOAD_PATH=@:@stdlib julia --startup-file=no \
  --project=julia/environments/formatter -m Runic --check --diff julia
```

Quality requires `JET.JET_AVAILABLE`, all Aqua checks and JET error analysis.
Runic has no configuration. The separate author and reviewer limit is 92
characters per line.

## Installer contract

The Python setup code runs one installer process per selected environment, with
the final runtime stack and preferences supplied in its environment:

```sh
julia --startup-file=no --project=ENGINE/environments/cpu \
  ENGINE/scripts/instantiate.jl INVENTORY.toml
```

The process requires exactly one private depot, no `artifacts/Overrides.toml`,
disabled user startup, and only the installed environments in `JULIA_LOAD_PATH`.
Its CondaPkg backend is `Null`, and setup supplies the Python executable for that
process only. It does not persist an originating Python environment path.

The installer fetches package sources before running any artifact selector,
checks their registered tree hashes, and audits each dynamic selector against its
pinned source. It calls Pkg's artifact collection with lazy artifacts included.
The audited LLVM and CUDA hooks also explicitly include lazy artifacts, because
Pkg does not forward that keyword into a dynamic selector. The selected metadata
is passed directly to Pkg's installer, preserving platform augmentation.

Every selected artifact must pass its tree-hash verification. Inventory paths
remain inside the private depot and contain every regular file and safe file
alias, including files accessed through directory symlinks. Escaping, broken and
cyclic links refuse setup. Existing corrupt package or artifact trees refuse;
missing trees may be downloaded. Python bytecode generation is disabled in this
standalone setup process so PythonCall cannot modify its package source tree
during precompilation. The adapter also sets `PYTHONDONTWRITEBYTECODE=1` before
initializing JuliaCall: a runtime cache miss can spawn the same standalone
precompilation process. This does not change an already running host Python
interpreter's bytecode policy.

Only after artifact checks and strict precompilation succeed does the script
atomically write a deterministic TOML inventory. During precompilation only, the
active environment moves to the front of the installed stack: Julia's parallel
precompiler otherwise cannot locate some weak dependencies present only in a
device manifest. Effective preferences must remain identical, and the installer
restores the runtime order even after a failure. Artifact selection and normal
runtime loading use the CPU-first stack described above.

Schema version 1 contains:

- `schema_version`, `complete`, `project`, and the host `platform` triplet;
- SHA256 of the exact `Project.toml` and `Manifest.toml` bytes;
- counts for packages, artifact selections and verified artifact records;
- `packages` entries with `name`, `uuid`, depot-relative `path`, selector kind
  (`none`, `default`, or `hook`) and sorted `selected_artifacts` names;
- `artifacts` entries with `name`, `package_uuid`, `tree_hash`, the path
  `artifacts/<tree_hash>` and sorted file paths relative to that artifact.

The package inventory includes every manifest entry with a source tree hash,
including separately packaged standard libraries. The engine and bundled
standard libraries are verified through the setup's engine and runtime identity.
Empty package or artifact lists remain TOML arrays. The Python publisher verifies
the inventory before publishing an immutable setup and checks it offline before
starting Julia or loading a device extension.

## CUDA selection

`cuda/runtime.toml` records the default toolkit minor release shared by the pinned
Runtime and Compiler packages. Both preference namespaces must select the same
version, for example:

```toml
[CUDA_Runtime_jll]
version = "13.4"

[CUDA_Compiler_jll]
version = "13.4"
```

This selects artifacts without querying a driver and supports setup on a node
without a GPU. The pinned Runtime package's list ends at 13.4 even though its
Compiler counterpart also provides 13.5. For an explicitly requested system
toolkit, both namespaces instead contain `local = true` and omit `version`.
Local selection requires that toolkit to be discoverable on the setup host.
