# Experimental Julia backend

**Experiment — draft for collaboration, not for merge. No CI qualification.**
Start with the [status, measured results and next-work list](STATUS.md). This branch
now targets schema 35 after merging the native CPU optimisation branch and its
SEP 34 medium-flux dependency. Spatial statistics use the shared flux implementation;
the Julia numerical kernels are unchanged.

This source-only CPU prototype implements solprop schema 35 behind
`backend="julia"`. It is an isolated experiment, authorised before a production SEP.
It preserves automatic backend selection and Python frontend signatures. The
[manual](../docs/guide/performance/julia.md) describes the supported cases and example.

## Prepare a checkout

Install [uv](https://docs.astral.sh/uv/getting-started/installation/) and Git first.
Use this branch's source checkout, not a released solprop wheel. On Apple Silicon
or Linux x86_64:

```sh
git clone --branch feature/julia-backend-prototype https://github.com/LupoLab/solprop.git solprop-julia
cd solprop-julia
uv sync --python 3.14 --extra julia
uv run --no-sync python julia/bootstrap.py
SOLPROP_JULIA_THREADS=1 uv run --no-sync python julia/example.py
SOLPROP_JULIA_THREADS=4 uv run --no-sync python julia/example.py
```

For an existing checkout, start at `uv sync`. Native is optional and is not needed
for these example runs. Bootstrap needs network access and several GB of disk
space for the runtime, packages and compilation caches; the first propagation can
spend substantially longer compiling than later windows spend propagating. The
example is a short four-mode Kerr capillary, ending at 0.1 mm, and prints a completion
message. It keeps output in memory. More geometries are shown in the manual.

The bootstrap downloads the official Julia 1.13.2 archive, verifies its SHA256 against
the digest published in Julia's
[release manifest](https://julialang-s3.julialang.org/bin/versions.json), and installs
it in ignored `.julia-runtime/`. Packages and caches live in ignored `.julia-depot/`.
It never uses the user's Julia executable, startup file or global environment.
`Project.toml` records direct dependencies; `Manifest.toml` is generated by Julia Pkg.
JuliaCall and PythonCall are pinned together to 0.9.37 for this experiment.
The loader refuses an unprepared checkout and never downloads on import.

After setup, use `uv run --no-sync` for experiments so optional installed packages
are retained. A plain `uv sync` can remove JuliaCall or a separately installed
native build. Do not import `juliacall` before solprop constructs the backend;
start a fresh Python process when changing runtime, thread or provider settings.
Unset conflicting `PYTHON_JULIACALL_*` or `JULIA_*` overrides if the loader names one.
If the archive checksum fails, remove only the named archive from `.julia-runtime/`
and retry bootstrap; do not bypass verification. Runtime cleanup is confined to
this checkout's `.julia-runtime/` and `.julia-depot/` directories.

## Start a small Julia/native comparison

First install the compiler and FFTW prerequisites from the
[native build guide](../docs/guide/performance/building-native.md). Then:

```sh
uv sync --python 3.14 --extra julia --extra native
PYTHONPATH=. uv run --no-sync python julia/core_compare.py \
  --arms julia/arms-cpu.json --widths 1 4 --rounds 3 --repeats 2 \
  --case rdw:fixed-rk --output .benchmarks/julia-native-rdw
```

This is one bounded ten-step case, with one warm-up and six warm samples per
backend/width. Choose a new output directory each time. `arms-cpu.json` uses the
current interpreter's native build and the default Julia BLAS provider with FFTW;
Julia BLAS is explicitly serial, while native keeps the harness's budget policy.
These are controlled configurations, not an assertion that every library uses the
same actual worker count. Inspect `samples.json` and each worker's provenance.
For the optimised Apple Silicon native comparison, follow the
[NEON FFTW build instructions](../docs/guide/performance/building-native.md) and
verify the loaded FFTW/OpenMP paths. A native build using the older Homebrew FFTW
library does not include the codelet improvement measured in the updated ledger.
`differences.json` compares retained final fields; it is not a pass/fail accuracy
certificate. No Numba arm is included in this starter comparison.

Add `--case ctc:fixed-rk` or `--case radial_filament_256:fixed-rk` when ready.
The large Cartesian cases need much more memory and time; start small. Read
[the ledger](../docs/dev/benchmarks.md#experimental-julia-cpu-prototype) before
comparing timings across machines, providers or observation policies. The tools
below also retain earlier development experiments for reproducibility.

## Check and measure

```sh
uv run --no-sync python julia/interop.py
SOLPROP_JULIA_THREADS=4 uv run --no-sync python julia/interop.py
uv run --no-sync pytest tests/backends/test_julia.py
JULIA_DEPOT_PATH="$PWD/.julia-depot" JULIA_LOAD_PATH='@:@stdlib' \
  JULIA_CONDAPKG_BACKEND=Null JULIA_PYTHONCALL_EXE="$PWD/.venv/bin/python" \
  .julia-runtime/julia-1.13.2/bin/julia --startup-file=no --threads=4 \
  --project=julia julia/test/runtests.jl
uv run --no-sync python julia/benchmark.py
```

The benchmark runs separate processes at 1, 2, 4 and the physical-core limit, without
duplicate widths. Each of three rounds alternates backend order and takes five warm
repeats. Both backends use FFTW `ESTIMATE`, identical thread limits, FSAL, four or
sixteen modes, and ten prescribed 10 µm steps. It reports construction and first-window
costs separately. Observation and shared host statistics have their own timer.
Generated JSON and field witnesses stay under ignored `.benchmarks/`.
Add `--mode-averaged` to `benchmark.py` or `compare.py` to measure the same pulse and
ten-step window using one amplitude and one effective-area nonlinear node. For a
three-backend Mac comparison:

```sh
uv run --no-sync python julia/compare.py --mode-averaged --blas-threads 1 \
  --arms numba_cpu native julia-accelerate-fftw --output .benchmarks/mode-averaged
```

Use `--radial` instead to compare 64- and 256-node axisymmetric Kerr beams at
0.9 critical power in constant argon. Both use the same ten prescribed 10 µm steps,
one or four numerical/FFT threads, and the declared BLAS width. Radial spatial
statistics have their own timer, separate from propagation. The shared Julia
matrix pipeline consumes the translated Hankel maps and the shared spatial-loss
matrix; no new transform package is required.

Use `--cartesian` for 32×32 and 64×64 Cartesian grids spanning ±500 µm, with the
same pulse, material, time grid and prescribed steps as the radial cases. This path
uses FFTs rather than BLAS contractions. The seam's compact separable operator is
evaluated per stage; a single forward/inverse pair replaces cached stage volumes.
The default spatial statistics are timed separately. On Linux compare
`numba_cpu native julia-openblas-fftw julia-mkl-mkl` to distinguish FFT providers;
changing BLAS alone cannot accelerate this Cartesian propagation path. Add
`--sizes 256` to compare a larger transverse grid at the same time resolution.
Worker records include explicitly owned bytes and peak process resident memory;
the latter also includes frontend arrays, library workspace and temporary copies.

`--worker julia --profile` additionally writes a Julia sampling profile; provide an
existing output directory and an output JSON path when running a worker directly.

The numerical core uses native Julia arrays, planned FFTW transforms and BLAS `mul!`.
AcceleratedKernels supplies task scheduling and the generic loop implementation over
KernelAbstractions. A small CPU Kerr traversal shares the scalar product with the
generic loop, but visits contiguous time columns to avoid costly index division.
Constant-table stage propagators are cached for exactly equal step lengths and
rebuilt when an adaptive trial changes the step. CPU pointwise loops traverse
contiguous columns, use SIMD, and require at least 32768 samples per task.
No umbrella fast-math or reassociation of protected reductions is enabled.

The modal FFT cap is `SOLPROP_FFTW_THREADS`. Raman convolution and transverse
plans accept independent `SOLPROP_JULIA_RAMAN_FFT_THREADS` and
`SOLPROP_TRANSVERSE_FFTW_THREADS` limits. Modal and doubled-grid Raman plans
default to serial below 16384 real-side samples, otherwise up to four workers;
the transverse default follows the modal cap. Mode-averaged BLAS defaults to one
worker. Explicit overrides remain available. Plan widths are
recorded in backend metadata. The kernel-construction FFT is serial and outside
the measured propagation window.


`SOLPROP_FFTW_PLAN=estimate|measure|patient` selects Julia's planning effort;
`estimate` remains the experimental default. Measured plans spend additional time
at construction choosing algorithms for the actual array layout and thread count.
Planning is excluded from warm propagation timings and recorded separately.
`julia/compare.py --plan measure` applies the same request to all compared backends.
No FFTW wisdom is imported by this experimental Julia adapter.

GPU execution is not implemented or qualified. CUDA/AMDGPU array allocation, FFT plans,
device-safe reductions and synchronization still need adapters and device tests;
the presence of KernelAbstractions/GPUArraysCore in the dependency graph does not
establish GPU support. Metal, Float32, runtime distribution and compilation-cache
engineering remain future work.

## Provider and compiler experiments

`SOLPROP_JULIA_BLAS=openblas|accelerate|mkl` selects BLAS before constructing the
first backend. AppleAccelerate is the macOS default; other prepared platforms
default to OpenBLAS. AppleAccelerate requires macOS;
MKL is qualified here only on Linux x86_64. Accelerate's threading API selects
single-threaded or library-managed parallel execution, not an exact worker count.
For controlled comparisons set `SOLPROP_BLAS_THREADS=1`. The comparison runner
sets MKL's global and FFT limits to the requested numerical width and its BLAS
domain separately, so `--blas-threads 1` does not cap MKL FFT execution. See
[Intel's domain thread controls](https://www.intel.com/content/www/us/en/docs/onemkl/developer-guide-windows/2025-0/mkl-domain-num-threads.html).

FFTs remain FFTW independently of BLAS. AppleAccelerate 0.7 also extends AbstractFFTs;
the engine deliberately plans from strided views to retain FFTW plans. To experiment
with MKL FFTs in an isolated checkout, call `FFTW.set_provider!("mkl")` with the private
runtime and project, then restart Python. Restore with `FFTW.set_provider!("fftw")`.
The preference belongs only to that checkout and is not committed.
MKL's FFTW compatibility layer ignores FFTW planning-rigor flags; a recorded
`measure` request is not evidence that MKL performed FFTW's measured search.
See [Intel's FFTW wrapper documentation](https://www.intel.com/content/www/us/en/docs/onemkl/developer-reference-c/2024-1/using-fftw3-wrappers.html).

`julia/tune.py --compare-blas accelerate --modes 16 --output .benchmarks/blas.json`
alternates providers and Numba in one process after warming. On Linux use
`--compare-blas mkl`. Explicitly set the Julia, Numba, FFT and BLAS thread limits
before launching. `--baseline PATH` also loads a saved numerical module for an
alternating before/after comparison. The runner records source digest, thread
settings, raw timings, source counts and numerical differences, and rejects a
failed rounding screen. It does not establish adaptive accuracy by timing alone.

The measured compiler settings remain native CPU targeting, normal inlining, `-O2`,
and automatic bounds checking with local `@inbounds` in validated kernels. An
alternating `-O3` experiment did not improve the declared case. LLVM output confirms
packed double-precision SIMD arithmetic in the Kerr loop; protected error reductions
retain their ordered arithmetic. See the benchmark ledger for measured effects.

The optional `--numba-tabulate` arm checks Numba's tabulated-propagator setting
against its default. On Linux, a mixed Julia/MKL and Numba process can interact with
OpenMP affinity. Use fresh backend processes (`benchmark.py --worker ...`) and
unset `OMP_PLACES` and set `OMP_PROC_BIND=false` for the final comparison; restrict
both processes to the same CPU set externally. Same-process provider sweeps are
useful pilots, but do not replace this isolation check.

Provider interfaces: [AppleAccelerate](https://github.com/JuliaLinearAlgebra/AppleAccelerate.jl),
[MKL.jl](https://github.com/JuliaLinearAlgebra/MKL.jl), and
[FFTW's provider preference](https://juliamath.github.io/FFTW.jl/stable/).

For a fresh-process comparison with native and provider attribution, build native in
this checkout, then run:

```sh
uv sync --extra native --extra julia
uv run --no-sync python julia/compare.py --blas-threads 1 --output .benchmarks/mac-providers
# Linux: native uses the providers chosen at build time.
uv run --no-sync python julia/compare.py --arms numba_cpu native \
  julia-openblas-fftw julia-mkl-fftw julia-mkl-mkl --output .benchmarks/linux-providers
```

The runner alternates three rounds of five warm windows per arm, at one and four
threads. It records native build information, actual loaded thread pools, NumPy's
BLAS configuration, source counts and final-field witnesses. On macOS both the
installed NumPy/SciPy and native build may already use Accelerate; inspect their
records rather than assuming Numba uses OpenBLAS. `benchmark.py --worker native
--propagator-mode tabulate` records the requested policy, but source inspection
shows that native's resident DOPRI5 path still forms its flows per stage; the
native low-storage integrator has the distinct table option. Removing `SOLPROP_NATIVE_KERNEL_THREADS` and `SOLPROP_NATIVE_FFT_THREADS`
while keeping its global cap exercises native's automatic operation sizing.

## SEP 30 core cases

The scalar CPU subset includes one field-plasma channel, constant scalar Raman,
longitudinal stage expansions and resident exponential Adams. Cartesian envelopes
also execute the existing prescribed RK4IP scheme. Run the frozen core definitions
through the standard harness, including its declared output/statistics windows:

```sh
uv run --no-sync python -m benchmarks list --set core --backend julia
uv run --no-sync python -m benchmarks run --set core --backend julia --mode quick
uv run --no-sync python -m benchmarks run --set core --backend julia --track fixed-rk
```

Use the ordinary machine-profile and reference qualification process for publishable
standard comparisons. `core_screen.py` is an additional development tool: it times
propagation only, saves final fields/statistics, and records setup and first-call costs.
Its adaptive timings exclude the standard harness's observations. The focused checks
are in `tests/backends/test_julia_core.py`. Unsupported geometries, response combinations
and integrator variants fail explicitly; see the manual for the scope.

Cartesian and line field grids also support one scalar plasma channel, including
accepted-field population diagnostics. Their current is evaluated in physical-space
chunks before the transverse forward FFT. Focused source, short DOPRI/RK4IP,
absorber, chunk-tail and memory checks are in
`tests/backends/test_julia_cartesian_plasma.py`. The retained strided FFT layout
uses parallel large copies and inverse normalization, a protected real-root branch,
and omits additive absorber transforms only when their rates are exactly zero.
`tests/backends/test_julia_zero_absorber.py` checks both inactive and active losses.
Exactly zero plasma-rate columns without initial electrons omit current integration
and clear reused outputs. `tests/backends/test_julia_zero_plasma.py` checks reuse
after an ionising source and retention of pre-existing electrons.
Modal and radial sources also skip additive transforms for exactly absent loss
rates; `tests/backends/test_julia_modal_zero_absorber.py` checks active and absent
losses under both temporal schemes.

The mode-averaged envelope extension executes `gnlse_soliton` and
`gnlse_raman_shock`, using the existing frontend and translated Kerr/Raman/shock
coefficients. Both DOPRI and Adams share the scalar engine. The corresponding
short source, propagation, absorber and reset checks are in
`tests/backends/test_julia_envelope.py`. The long-pulse hydrogen and argon
blueshift mode-averaged field cases use the already supported plasma/Raman path.
